Fin Ray Gripper with Integrated Tactile Sensing

A compliant, TPU-printed Fin Ray gripper with a resistive tactile array built into its fingers — grip response adjusts automatically based on real-time slip and motion detection.

Mechanical DesignBio-InspiredEmbedded SystemsSignal Processing
View on GitHub ↗ Read the full build →

Overview

A 3-person team project at NYU Tandon (ROB-GY 6103) with Amey Joshi and Dana Sy-Ching. The goal was to close a real gap in soft robotics: Fin Ray grippers adapt passively to object shape, but almost none of them can feel what they're holding. We built one that could, and could react to it.

Mechanical Design

The fingers are 3D-printed in TPU and driven by a mechanical parallelogram off a high-torque servo, letting the gripper passively wrap around irregular objects with no active control needed. Iterating on the finger geometry, I found diagonal crossbeams held up better than perpendicular ones for flexibility, and curved outer edges distributed grip force and stability far better than a triangular profile.

Tactile Sensor & Electronics

Built a resistive tactile array from copper tape sandwiching a Velostat pressure-sensitive sheet, arranged in an 8×4 matrix sized to fit directly onto the gripper's finger. Read the array through a CD74HC4067 16-channel multiplexer into a Parallax Propeller microcontroller running a dual-cog architecture — one core dedicated to scanning the sensor matrix and streaming data out, the other to receiving grasp commands and driving the servo — talking to the host over full-duplex serial.

Grip Control Logic

Implemented a closed-loop state machine (NO_CONTACT → INITIAL_CONTACT → STABLE / MOTION / SLIP) driven by the Center of Pressure shift between frames. On the Python side, raw 8×4 voltage readings get converted to pressure, upscaled to 80×40 via bicubic interpolation, and used to track Center of Pressure and its frame-to-frame delta — crossing set thresholds triggers a soft or power grip response, with the servo closing faster automatically the moment slip is detected. I also layered in a finite-element force estimate (F = KU, using stiffness models built for the test objects) to get a more physically grounded read on contact force than the CoP threshold alone gives.

The live grip-state dashboard — pressure map, CoP trail, and slip/motion classification, running in real time off the sensor matrix.

What Broke, and How I Fixed It

Copper tape kept tearing at the flex points from repeated motion — fixed it by soldering short lengths of stiff wire to soft lead wire at each junction so the joint could absorb the flexing instead of the tape. Doubling up Velostat layers made the array too resistive to get usable readings, so I kept it to a single loose layer instead, which improved variability. Inconsistent readings coming off the multiplexed rows turned out to be a circuit topology problem — switching from a high-signal to an active-low design fixed it.

Cost

Built for about $67 in parts total — TPU-printed gripper, high-torque servo, copper tape, Velostat, multiplexer, birch plywood housing — kept deliberately low-cost so the design could be replicated by others.

Visual Tactile Sensor Development

A silicone-elastomer tactile sensor with a reflective membrane and an onboard camera, reconstructing contact depth and surface geometry from video in real time.

Sensor FabricationComputer VisionEmbedded Systems
View on GitHub ↗ Read the full build →

Fabricating the Sensor

Mixed a two-part silicone elastomer (Ecoflex 00-45) 1:1 by weight and cured it for about 5 hours. A laser-cut paper template printed an even marker grid onto the surface for tracking deformation. Brushed on a reflective membrane — bronze flake mixed into silicone, two coats cured 2 hours each — to get a uniform, durable reflective layer, then mounted the finished elastomer onto a support plate.

Assembly & Electronics

3D-printed the housing (PLA shell, clear-resin core/spacer), glued the elastomer onto a transparent acrylic core, and mounted a 2×4 RGB LED array for illumination plus a Raspberry Pi camera to capture surface deformation.

The full rig — Raspberry Pi, breadboard, and the finished sensor (shown next to coins for scale).

Reconstructing Contact from Video

The Raspberry Pi processes the camera feed and reconstructs depth maps and surface normals in real time using shape-from-shading, then passes tactile information to an Arduino for feedback — for example, driving an LED panel to visualize applied force.

Depth map and surface normals reconstructed live from the sensor's camera feed.

Where This Could Go

Because it captures detailed contact geometry rather than just a single force reading, this approach extends naturally to finer robotic manipulation, healthcare applications, and material identification — anywhere a robot needs to "feel" more precisely than a simple pressure sensor allows.

ATMOS Free-Flyer Platform

Redesigned a free-flying space robot using air-bearing systems and full avionics integration, creating a high-fidelity validation platform for autonomous space robotics algorithms. Led the hardware team integrating Nvidia Thor and Pixhawk with QGroundControl.

Pixhawk 6cPX4ROSSystems Integration
EDIT: add project link → Read the full build →

ATMOS is a free-flying testbed for validating autonomous space-robotics algorithms in microgravity-like conditions — built to support In-Orbit Servicing tasks like debris collection, panel fastening, and valve manipulation, in the spirit of platforms like Astrobee and SPHERES.

System Architecture

A pilot inputs commands through a USB game controller into QGroundControl, which relays mission parameters to the vehicle over WiFi. An onboard Nvidia Jetson receives MAVLink packets, runs the USB camera feed, and drives the robotic arm through ROS nodes. Flight commands pass from the Jetson to a Pixhawk flight controller over a dedicated MAVLink UART link, which outputs PWM signals to the thrusters.

The full stack — avionics on top, actuation plate below, air-bearing pucks at the base.

Electrical Architecture

Split the vehicle's electronics into two isolated plates to keep high-power actuation away from sensitive logic. The Avionics Plate centers on a Pixhawk 6c, wired out to dual telemetry ports, redundant GPS and power inputs, a CAN bus, and PWM actuator outputs. The Actuation Plate handles the high-power side — bottom and top solenoid banks (S1X/S2X) fed through buck/boost converters for stable 12V delivery, plus control logic for four thruster motors (M1–M4).

Ground Control & Flight Setup

Brought the vehicle up in QGroundControl end to end — flashing the PX4 stack, selecting the free-flyer airframe, running the guided sensor calibration (compass, gyro, accelerometer), mapping radio channels, and configuring COM_RC_IN_MODE to hand control over to a MAVLink joystick instead of a traditional RC receiver. Mapped a standard 3-position switch to Position, Altitude, and Return flight modes for safety.

What's Next: V2

Planning a bimanual upgrade — a second manipulator so the robot can hold an object steady with one arm while working on it with the other, which is core to real In-Orbit Servicing tasks. V2 also integrates the base and actuation plates into a single structural chassis to cut vibration transfer and lower the center of mass, and migrates onboard compute to an Nvidia Thor to run uncompressed visual SLAM and real-time trajectory optimization onboard, without offloading to a ground station.

Climbot — Stair-Climbing Robot

A six-wheeled, rocker-bogie stair-climbing robot built around a bare-bones BS2 microcontroller — proving that even limited hardware can coordinate motors, servos, and sensors to climb stairs.

Mechanical DesignEmbedded SystemsSensor Integration
EDIT: add project link → Read the full build →

Overview

Built around a deliberately constrained platform: the Parallax BASIC Stamp 2 (BS2), a microcontroller with far less processing power and memory than the boards most stair-climbing robots use. The goal was to see how far basic hardware could be pushed toward a task normally reserved for more capable systems.

Mechanical Design

Modeled the chassis in Onshape and settled on a rocker-bogie suspension — the same family of mechanism NASA's Mars rovers use — for its simplicity and minimal linkage count. Laser-cut the frame from wood to keep it lightweight, with a locking mechanism built into the connecting planks to stop the structure deforming under load. Six wheels — two each at front, middle, and rear — are each driven by their own DC motor, with two servos at the middle link responsible for lifting the front section during a climb.

Sensing & Control

An IR emitter/detector pair feeds the BS2 a signal whenever a stair edge is detected. On detection, the BS2 commands the servos to rotate the front link upward, reducing the effective height the robot needs to climb; once the front wheels clear the step, the servos return to neutral and the DC motors ramp back up to pull the robot fully onto the stair. Three motor driver boards manage the six DC motors, working around the BS2's limited pin count.

The finished build — BS2, motor drivers, and battery packs wired up on the chassis.

What Broke, and How We Fixed It

The BS2 executes code strictly line-by-line, so the DC motors would stall out while the servos were mid-move — fixed by ramping motor speed up gradually in PWM steps instead of switching it on abruptly. Standard 6V servos didn't have enough torque to lift the front link reliably; found a workable PULSOUT range (around 1250, against a neutral of ~1000) through trial and error. Getting a clean, sufficiently-currented 12V supply from batteries was harder than expected — custom battery packs leaked current, so most testing ran off a bench supply instead. Initial IR alignment was too sensitive to uneven terrain until we swapped in a more robust sensor.

Results

Climbot moved smoothly on flat ground and reliably climbed low-height steps once the servo pulse values were tuned. Load capacity was limited by the standard servo's torque, but the trials confirmed the core idea: even heavily constrained hardware can coordinate multi-motor, multi-sensor stair-climbing behavior.

Fusion 360 to ROS 2 URDF: The Real-World Guide

January 2026 · 10 min read

The real-world guide to exporting complex, nested Fusion 360 assemblies into ROS 2 without losing your mind or your coordinate systems.

Read article →

Complementary Documentation for: fusion2urdf-ros2 by dheena2k2 ↗

The standard README assumes you are a Linux pro and your CAD file is perfect. In reality, you will hit weird structure issues and terminal errors. This guide covers the "hidden steps" required to get a complex, nested Fusion 360 assembly into ROS 2.

1. Preparing the CAD (The "Cut & Paste" Method)

You do not need to flatten your entire assembly into a list. You can keep your Nested Structure (components inside components), but you must ensure the physics bodies are in the correct container. The most common mistake is having the robot's chassis bodies floating in the generic "Main File" rather than inside the base_link component.

Step 0: Break All Constraints First

Before you move anything, you must free your components from Fusion's constraints. If you try to Cut & Paste a body that is locked, Fusion will error out.

  1. Break Links: If you see a "chain link" icon on any component, right-click it and select Break Link. This disconnects it from external files.
  2. Delete Rigid Groups: Look in the browser for a folder named "Rigid Groups". Delete it entirely. Do not use Rigid Groups for ROS.
  3. Unground Everything: Look for any component with a "Pushpin" icon (red or gray). Right-click and select Unground.

Figure 1: The correct hierarchy. Note that bodies are inside base_link, not floating at the top level.

Step A: The "Base Link" Container

  • Create the Component: Right-click the top-level file name in the browser and select New Component.
  • Name it: Name it exactly base_link.
  • Note: If Fusion names it base_link (1), you have a duplicate name hidden somewhere. Find it and delete or rename it, or the script will fail.

Step B: Moving the Bodies (Cut & Paste)

Your chassis parts (plates, brackets, screws) are likely scattered as "Bodies" inside various folders. You need to move them into the base_link component.

  1. Activate Base Link: Click the small circle next to your base_link component to activate it.
  2. Enable Body Selection: By default, Fusion selects faces. Go to the top toolbar: Select > Selection Priority > Select Body Priority.
  3. Select & Cut: Select all chassis bodies (hold Shift). Press Cmd+X (Mac) or Ctrl+X (Win).
  4. Paste: Press Cmd+V (Mac) or Ctrl+V (Win).
  5. Result: The bodies move from the old folder into base_link, keeping their exact position in 3D space intact.
  6. Ground: Right click on base_link and select "Ground to Parent".

2. Joint Configuration

  • Use As-Built Joints (Shift + J): Since your design is already assembled in the correct shape, do not use standard "Joints" (which move parts). Use "As-Built."
  • Selection Order: When making a joint, select the Child (moving part) first, then the Parent (stationary part). Example: click Wheel → click base_link.
  • Types: Revolute for wheels and arms; Rigid for locking sub-assemblies together (e.g. locking a LIDAR sensor to the chassis).

Figure 2: The As-Built Joint menu. Ensure the correct Motion Type is selected.

3. Terminal & Script Installation

If you are not used to the command line, the standard installation instructions can cause zsh: parse error or No such file errors.

Common Error 1: The "Placeholder" Trap

Error: cd: no such file or directory: <path to fusion2urdf-ros2>

Cause: The text <path to...> is a placeholder.

The Fix: Type cd (with a space), then drag and drop the folder from Finder/Explorer into the terminal window.

Common Error 2: The "Wrong Directory"

Error: cp: ./URDF_Exporter_Ros2: No such file or directory

The Fix: Always check where you are before copying. Run ls. If you don't see the script in the list, you are in the wrong folder.

The Correct Command Sequence (Mac Example)

# 1. Go to your downloads (or wherever you cloned it)
cd ~/Downloads/fusion2urdf-ros2

# 2. Verify the file is actually there
ls
# (You should see 'URDF_Exporter_Ros2' in the output)

# 3. Copy the script to the Fusion 360 Script folder
cp -r URDF_Exporter_Ros2 "$HOME/Library/Application Support/Autodesk/Autodesk Fusion 360/API/Scripts/"

4. Final Checklist Before Export

  • Name Check: Top component is base_link (no space, no (1)).
  • Body Check: base_link contains the chassis bodies (not sitting in a generic "Component1").
  • Constraint Check: All Rigid Groups deleted; all components Ungrounded.
  • Joint Check: Only Rigid or Revolute joints used. No red/yellow warnings.
  • Orientation: Red axis (X) points Forward. Blue axis (Z) points Up.

QGroundControl Setup

December 2025 · 8 min read

A comprehensive overview of setting up QGroundControl for MAVLink-enabled robots and PX4 stacks for autonomous flight missions.

Read article →

The Summary

QGroundControl (QGC) provides full flight control and mission planning for any MAVLink-enabled robot. The primary goal is to provide an easily editable user interface for the developer to configure. It serves as the primary ground control station for the PX4 autopilot stack.

QGC allows operators to plan complex autonomous missions on a desktop and also provides visual data coming from the vehicle.

Figure 1: High-level connection architecture between QGC and the Vehicle.

Technical Workflow: PX4 Integration

1. Installation

Installation directions at the QGC User Guide ↗.

# Ubuntu Permission Setup (User to dialout group)
sudo usermod -aG dialout $USER

# Remove modem manager (interferes with serial ports)
sudo apt-get remove modemmanager -y

# Install GStreamer (required for video streaming)
sudo apt install gstreamer1.0-plugins-bad gstreamer1.0-libav

2. Initial Configuration

Once QGC is running, connecting a vehicle's flight controller via USB automatically triggers the setup logic. The Vehicle Setup view (gear icon) is where the core configuration happens:

  • Firmware: QGC detects the board (e.g. Pixhawk) and offers to flash the stable PX4 Pro stack.
  • Airframe: Select the specific vehicle geometry (e.g. Hexarotor X, Quadcopter, VTOL) or custom, then "Apply and Restart".
  • Sensors: A guided wizard walks you through calibrating the Compass (rotating the drone on all axes), Gyroscope (holding it still), and Accelerometer.
  • Radio: Requires moving the transmitter sticks to their limits to map channels and set min/max values.
  • Joystick: To enable joystick and disable RC mode, navigate to View → Parameters → search COM_RC_IN_MODE.

Figure 2: Configuring COM_RC_IN_MODE to enable MAVLink joystick control.

3. Flight Modes & Safety

For PX4, you map specific RC switches to flight modes. A common setup involves a 3-position switch configured for:

  1. Position Mode: GPS-assisted hovering (easiest for beginners).
  2. Altitude Mode: Maintains height but drifts with wind.
  3. Return Mode: Automatically returns the drone to the launch point.

4. Mission Planning & Operation

The Plan View allows you to click on the map to place waypoints. For surveying, the "Pattern" tool automates the creation of grid flights for aerial mapping.

During flight, the Fly View displays the live video feed (if configured) and critical telemetry like battery voltage, satellite count, and altitude.

My Perspective

In the robotics ecosystem, the "user experience" is often an afterthought, but QGroundControl changes that narrative. While Mission Planner (the alternative GCS) offers incredibly deep parameters for debugging, QGroundControl shines in its modern, intuitive interface.

For field operations, the ability to run QGC on an iPad or Android tablet is a game-changer. It reduces the amount of heavy gear required and simplifies the pre-flight checklist. The touch-optimized interface makes dragging waypoints and adjusting mission parameters feel natural rather than technical.

Ultimately, if you are developing new vehicle types or need deep log analysis, you might stick to Mission Planner. But for reliable day-to-day operations and a setup workflow that doesn't require a manual to understand, QGroundControl is the superior choice.
